## 边界校验与集成测试补强

**背景**：当前核心链路已经能跑通，但不少保障仍停留在“单点单测 + 手工回归”。后续如果继续迭代首页、通知、登录态和内容流，建议把更多防御性校验前置到接口层、store 层和关键副作用边界。

### 建议补强方向

- 对分页参数、排序参数、搜索词长度做统一校验与兜底，避免非法 query 直接穿透到数据库查询
- 对 SSE 事件 payload 做更严格的字段校验，避免旧客户端或异常数据把前端状态打脏
- 对 store 中“分页 / 排序 / 搜索 / 静默刷新”这类复合状态增加更多回归测试，防止互相覆盖
- 为 `/api/posts`、`/api/auth/refresh`、`/api/stream` 等关键接口补集成测试，而不只测工具函数
- 对前端关键异步链路补失败态保护，例如重复点击、竞态返回、页面切换中途响应落回

### 优先级建议

- 先补首页 feed、登录态刷新、通知轮询 / SSE 边界的集成测试
- 再逐步下沉到管理端、AI、公告等次级链路

## 安全与滥用防护补强

**背景**：这里说的“防御性编程”不是指普通参数兜底，而是面向真实攻击面做防护。当前站点已经完成 cookie 登录态，但验证码、上传、接口刷量、跨站请求等方面仍缺少系统性的反滥用措施。现在还能跑，不代表上线后扛得住恶意脚本、批量请求和资源滥用。

### 当前已确认的缺口

- `/api/verify/send` 发送验证码没有冷却时间、按 IP 限流、按邮箱日配额，容易被刷爆邮箱或被人拿去打接口
- `/api/verify/check` 没有错误次数上限和临时锁定，6 位验证码存在被暴力猜解的空间
- 开发环境未配置 SMTP 时，验证码会直接打印到服务端日志，若环境隔离做得不好，存在泄露风险
- 当前后端只开了 `cors({ origin: true, credentials: true })` 和 `express.json({ limit: '15mb' })`，缺少更明确的安全中间件与生产配置收口
- 图片虽然有限制单张 3MB、最多 9 张、总量 8MB，但仍是 base64 直接进库，缺少用户级别的上传额度、频率限制和资源清理策略
- 目前没有看到统一的接口限流策略，登录、发帖、评论、回复、举报、AI 等入口都可能被脚本高频调用

### 优先级最高

- 给验证码发送接口补三层保护：单邮箱冷却时间、单 IP 窗口限流、单邮箱日发送上限
- 给验证码校验接口补错误次数上限与短时锁定，超过阈值后强制重新发码
- 为登录、注册、重置密码、验证码相关接口接入 `express-rate-limit` 一类的基础限流
- 生产环境收紧 CORS allowlist，不再使用 `origin: true`
- 补 `helmet` 或等价响应头策略，至少先把常见安全头补上
- 基于 cookie 鉴权补 CSRF 防护方案，最小可行可以先落 `sameSite` 策略，后续再评估 CSRF token

### 上传与资源滥用防护

- 对图片上传增加更严格的“每用户 / 每日 / 每帖”配额，避免服务器被当作公共图床
- 对图片类型校验从“只验 data URL 头”继续下沉，补真实 mime / 文件签名校验
- 给长期无引用的图片、草稿图片、活动海报建立清理策略，避免存储无限增长
- 评估将图片从 MongoDB 内联 base64 迁移到对象存储或磁盘存储，数据库只存引用
- 对 AI、公告、活动等可能承载大文本或图片的入口单独设体积上限和频率限制

### 监控与审计

- 为验证码发送、登录失败、图片上传失败、限流命中建立审计日志，便于定位攻击来源
- 给高风险接口补基础监控指标，如每分钟请求数、失败率、单 IP 峰值
- 对异常行为设计自动告警阈值，例如单 IP 高频验证码请求、短时间大量图片上传、异常 401/429 激增

### 实施顺序建议

- 第一批先做验证码限流 / 爆破防护、登录注册限流、生产 CORS 收口、基础安全头
- 第二批做图片配额、上传签名校验、资源清理
- 第三批再做更细的 CSRF、审计面板、黑名单 / 风控策略

## 帖子流滚动偶发白块渲染毛刺

**背景**：主页帖子流在快速上下滚动时，偶发出现一块短暂的白色区域。当前判断更偏向前端卡片列表的绘制 / 合成瞬时毛刺，而不是后端、鉴权或 SSE 逻辑异常。

- 左侧栏、顶部栏和外围背景通常正常，说明更像局部卡片区域的瞬时掉帧
- 目前没有稳定复现步骤，暂不适合在提交前贸然改样式层

### 后续排查建议

- 用录屏或慢放确认白块是否总出现在新进入视口的帖子卡片位置
- 在独立分支里做“仅验证不正式修”的样式排查，例如临时降低卡片阴影、半透明背景或模糊层复杂度
- 若验证成立，再单独推进渲染稳定性修复，避免和业务改动混在一起

## 点赞通知语义优化

**背景**：当前通知中心会把同一帖子上的多条点赞通知合并显示。最低成本修复已改成“收到新的点赞”，避免把重复点赞事件错误表述成“3 人点赞”。

**后续优化目标**：让通知既能合并展示，又能正确表达“唯一点赞用户数”。

### 最低成本方案

- 保持现有通知模型不变
- 前端继续按帖子聚合同类点赞通知
- 文案只写“你的帖子收到了新的点赞”，不显示人数

### 推荐优化方案

- 在点赞通知中记录 `actorUserId`，表示是谁触发了这次点赞
- 后端为“同一用户 + 同一帖子 + 未读点赞通知”做去重或 upsert
- 用户取消点赞后，可选择删除对应未读通知或将其标记失效
- 前端聚合时按唯一 `actorUserId` 统计人数，再决定是否显示“3 人赞了你”

### 进一步可选项

- 若未来想做“谁赞了我”，可额外记录触发者昵称快照或匿名展示名快照
- 若未来想减少通知噪音，可只保留最新一条未读点赞聚合通知

## 登录态失效处理优化

**背景**：当前 access token 默认 15 分钟过期，refresh token 默认 7 天有效。当前仓库已经完成 cookie 化与运行时静默刷新，但仍可以继续增强登出吊销、编辑态提示与更细的会话管理。

### 当前问题

- `logout` 目前只清 cookie，没有服务端 refresh token 吊销机制
- 编辑中的用户如果最终 refresh 失败，仍可能在会话失效时被打断
- 会话模型已收口为 cookie + same-origin，跨域直连部署还没有作为正式支持路径维护

### 最低成本方案

- 为 refresh token 增加服务端可撤销能力
- 对编辑态补“会话失效”提示与临时草稿保护
- 如果未来要支持前后端分域直连，再补完整的跨域 cookie 配置与部署说明

### 推荐优化方案

- 在 `apiClient` 中做单飞 refresh，避免多个并发 401 同时刷新
- 区分 `TOKEN_EXPIRED`、`INVALID_TOKEN`、`USER_NOT_FOUND`，只对可恢复场景尝试 refresh
- 对“正在编辑”类页面补一个登录失效提示，避免用户误以为内容丢失

### 进一步可选项

- 后端为 refresh token 增加版本号、黑名单或持久化存储，支持主动失效
- `logout` 时同步吊销 refresh token，减少旧 token 在有效期内继续可刷新的风险
- 若未来需要更细控制，可按设备维度管理会话

## 内联图片传输瘦身

**背景**：当前帖子、评论/回复、活动、草稿都直接把 base64 Data URL 存在数据库并通过 JSON 接口返回。这样会把图片体积直接绑到主接口响应上，列表刷新越频繁，浪费越明显。

### 已确认情况

- `GET /api/posts` 当前会返回帖子完整 `images`
- `getDrafts()` 当前会返回草稿完整 `images`，但草稿列表页实际上不展示图片
- 活动与评论相关接口也存在同类问题，但是否能直接裁字段要看页面是否需要展示图片
- SSE 静默刷新只改善了交互，不会减少这部分传输量

### 第一阶段（最低成本，收益最高）

- 先拆分“列表 DTO / 详情 DTO”，不要默认所有接口都返回完整图片字段
- 第一刀优先落在草稿列表这类“不展示图片”的接口
- `backend/src/services/draftService.js#getDrafts()` 改成返回 summary DTO，不再携带 `image/images`
- 前端草稿列表页保持现有 UI，不需要同步做图片展示改动

### 第二阶段（视页面需求推进）

- 梳理“我的帖子”等列表页是否真的需要完整图片
- 对确实需要封面的列表，优先只返回首图或缩略图，而不是 9 张完整 base64
- 对详情页继续保留完整图片，避免一次性改动过大

### 长期方案

- 将图片从内联 base64 迁移到独立文件存储 / URL 引用
- 让浏览器缓存图片资源，而不是每次跟随 JSON 重新下载
- 再视情况统一处理帖子、评论、回复、活动海报、草稿图片

## 通知实时更新（SSE）✅ 已完成

**背景**：当前通知中心使用 `30s` 轮询，并在标签页重新可见时立即 `refresh()`。这套方案不够实时，也会产生空轮询请求，但实现简单、状态稳定。

### 已落地行为

- 后端在创建通知后，会向目标用户定向广播 `notification-updated`
- 前端收到事件后会刷新 `unreadCount` 和通知列表
- 现有 `30s` 轮询仍然保留，作为页面隐藏 / 断线 / 多标签页等场景下的兜底

### 现有方案的主要缺点

- 现在收到通知时会直接刷新通知列表，而不是只在通知面板打开时刷新，因此实现简单但请求量不算最省
- 轮询兜底仍然存在，多标签页同时在线时还是会有重复请求
- SSE 事件当前只表达“通知有更新”，不表达更细粒度的新增 / 已读 / 删除语义

### 后续优化方向

- 若后续要继续降请求，可改成：
  - 默认只刷新 `unreadCount`
  - 仅在通知面板打开时才刷新通知列表
- 若后续要继续增强实时体验，可考虑按事件类型区分“新通知 / 已读状态变化”
- 继续保留“服务端结果为准”的策略，不急着做前端本地增量拼接

### 暂不建议的扩展

- 不先做“每条通知通过 SSE 增量插入前端列表”
- 不先做点赞通知实时合并、去重和已读状态本地重算
- 等后续专门优化通知体验时，再评估是否从最小方案升级

## Safari 兼容性视觉收尾

**背景**：当前在 Chrome / Edge 上表现基本一致，但 Safari 上存在轻微的布局怪异或交互区域观感不自然的问题。现阶段看起来没有明显阻断主流程，因此不必在业务改动里顺手硬修，但值得单独留出一轮兼容性收尾。

### 当前判断

- 目前更像“兼容性瑕疵”，不是明显功能故障
- 高风险区域主要集中在 `fixed / sticky / backdrop-filter / transform / overflow` 叠加较多的页面
- 不建议在日常业务改动里顺手穿插大量 Safari 样式补丁，容易误伤 Chromium 已稳定的布局

### 优先排查页面

- `LandingPage`：固定导航、毛玻璃、大量 GSAP `transform / blur / scrollTrigger`
- `TopBar` 通知弹层：portal + fixed 遮罩 + backdrop blur + 安全区
- `AIPanel`：整屏 fixed + 侧滑面板 + 内部滚动容器
- `ImageLightbox`：fixed 全屏层 + 缩放 / 拖拽 transform
- 管理端 / 公告页各类弹窗：fixed 遮罩 + 内部滚动 + 模糊背景

### 后续排查方式

- 先录屏或截图固定问题页面，确认是视觉偏差还是点击命中异常
- 尽量优先排查层级与点击区域：
  - `z-index`
  - `pointer-events`
  - `fixed + transform`
  - `sticky + overflow`
- 再视情况做最小样式补丁，例如：
  - 降低部分 backdrop blur 复杂度
  - 减少会创建新合成层的 transform 叠加
  - 调整 Safari 上的安全区 / 高度计算

## AI 停止后的会话语义优化

**背景**：当前为避免“停止生成后下一轮串话”，后端采取了保守策略：一旦本轮 AI 生成被中断，会清理这轮未完成的用户消息/回复轮次。这样能先止住串话，但代价是用户刚输入的问题也会一起消失。

### 当前已落地行为

- 停止生成时，前端会显式调用服务端取消接口
- 服务端中断正在执行的 LLM 请求，避免被停止的回答继续落库
- 若该轮 assistant 未完整完成，后端会清理该轮未完成消息，防止下一轮继续接着答

### 后续优化目标

- 保留用户已发送的消息，不要因为点击“停止”而直接消失
- 为被中断的 assistant 回复引入明确的“已停止 / 未完成”状态
- 下一轮构造上下文时，忽略未完成轮次，避免模型继续补答上一次内容
- 前端在消息列表中给出清晰的中断反馈，而不是直接让整轮内容消失

### 可能实现方向

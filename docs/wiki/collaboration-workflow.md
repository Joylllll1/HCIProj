# 团队协作开发规范

> 本文件定义本项目的小组协作流程。目标不是增加流程成本，而是减少互相覆盖、带病提交、无人负责和合并后翻车。

## 适用范围

- 适用于所有进入仓库的代码、文档和配置修改
- 适用于前端、后端、文档、脚本、OpenSpec 变更
- 适用于 AI 辅助编写与纯手写代码

## 基本原则

1. `main` 只接收可运行、可合并、已自测的改动。
2. 不直接在 `main` 上开发功能或修 Bug。
3. 每个任务对应独立分支，任务范围尽量单一。
4. 提交前必须先完成本地自测，不能把“还没跑过”的代码直接推给别人收拾。
5. 合并前必须经过 Review；涉及安全、权限、匿名映射、认证、AI prompt 的改动要更谨慎。

## 分支规范

### 禁止事项

- 禁止直接在 `main` 上开发新功能
- 禁止多人共用同一个长期开发分支处理不同需求
- 禁止用含义模糊的分支名，如 `test`、`wjl`、`new`、`final2`

### 分支命名

推荐格式：

```text
feat/<module>-<summary>
fix/<module>-<summary>
refactor/<module>-<summary>
docs/<summary>
chore/<summary>
```

示例：

```text
feat/ai-web-search
fix/post-image-upload
refactor/comment-store
docs/team-collaboration-workflow
chore/global-optimization
```

### 新功能 / 修复流程

1. 先同步最新 `main`
2. 从 `main` 拉新分支
3. 在自己的分支上开发
4. 自测通过后再 push
5. 发起 PR 合并到 `main`

建议命令：

```bash
git checkout main
git pull
git checkout -b feat/<module>-<summary>
```

## 任务开始前要求

### 开发前先确认

- 需求范围是否明确
- 是否已有他人在改同一模块
- 是否需要先更新 OpenSpec / wiki / 设计说明
- 是否会影响接口、数据库结构、共享组件或全局状态

### 必须先沟通的情况

- 修改认证、权限、匿名映射、管理员操作、AI prompt、数据库模型
- 修改公共组件或全局 store
- 改动范围跨前后端
- 可能影响别人正在开发的模块

## 提交要求

### 提交前自查

提交前至少确认：

- 代码能运行
- 没有明显报错
- 没把调试代码、无关日志、临时文件带进去
- 没误改别人的文件
- 改动范围和任务目标一致

### 本地自测要求

#### 前端改动至少满足

- `npm run lint`
- `npm run build`
- 手动点一遍受影响页面和关键交互

#### 后端改动至少满足

- `npm run lint`
- 受影响接口手动验证一遍
- 如果涉及数据写入，确认异常路径也能正常处理

#### 前后端联动改动至少满足

- 前端 lint + build
- 后端 lint
- 关键主流程手动走通一次

例如：

- 发帖功能：发帖、保存草稿、从草稿发布至少测一遍
- AI 功能：发送消息、切换会话、重新生成至少测一遍
- 管理功能：正常路径和权限拦截路径都要测

### 禁止带病提交

以下情况不要 push：

- 本地 lint 没过
- 构建失败
- 主流程没测
- 知道有 bug 但没在 PR 里明确说明

## Commit 规范

### 提交信息格式

沿用现有约定，建议格式：

```text
[AI-assisted] feat(ai): add web search tool scaffold
[Human-written] fix(post): handle empty image drafts
[AI-assisted] docs: add collaboration workflow
```

要求：

- 必须标注是否使用 AI 辅助
- 必须写清模块和改动目的
- 不要使用 `update`、`fix bug`、`改一下` 这类无信息量描述

## Pull Request 规范

### PR 前提

只有满足以下条件才能发 PR：

- 分支已同步过最新 `main`，或已确认无冲突风险
- 本地自测完成
- 改动范围清晰
- PR 描述写清楚

### PR 描述至少包含

- 改了什么
- 为什么改
- 怎么测的
- 风险点是什么
- 是否影响数据库 / 接口 / 配置 / prompt

推荐模板：

```text
## 变更内容
- 

## 原因
- 

## 自测
- [ ] frontend npm run lint
- [ ] frontend npm run build
- [ ] backend npm run lint
- [ ] 手动验证：

## 风险与影响
- 
```

## Code Review 规范

### 最低要求

- 每个 PR 至少 1 人 Review 后才能合并
- 涉及安全、权限、认证、匿名映射、管理员操作、数据库结构、AI prompt 的改动，至少 2 人看过再合并

### Review 时重点看什么

- 功能是否真的满足需求
- 有没有明显逻辑漏洞
- 是否引入行为回归
- 命名和分层是否符合项目约定
- 是否有无关改动混入
- 是否缺必要测试或手动验证

### Review 意见处理

- 提 Review 的人要指出具体问题，不要只说“有点怪”
- 改代码的人要逐条处理，不要口头说“应该没事”
- 如果有争议，以文档、代码事实、运行结果为准，不靠感觉拍板

## Merge 规范

### 合并前必须满足

- PR 已通过规定的 Review
- CI 至少没有基础结构错误
- 本地自测已完成
- 没有明显未解决讨论

### 合并方式

- 小功能、单主题 PR：优先 `Squash and merge`
- 需要保留完整提交历史时再考虑普通 merge
- 不建议把很多无关 commit 原样塞进 `main`

### 禁止事项

- 禁止未经 Review 直接合并自己的 PR
- 禁止“先合并再修”
- 禁止把多个不相关需求合在一个 PR 里

## 紧急修复

如果线上出现明显故障，可走紧急修复流程：

1. 从 `main` 拉 `fix/<module>-<summary>` 分支
2. 只修当前故障，不顺手夹带重构
3. 最小自测完成后立即提 PR
4. 至少找 1 人快速 Review
5. 合并后补充记录故障原因和后续优化事项

## AI 协作补充要求

- AI 可用于生成样板、重构、补文档、辅助排查
- AI 生成代码不能免 Review
- 使用 AI 后，提交人仍对代码结果负责
- 涉及安全逻辑、权限判断、数据库迁移、匿名映射的关键部分，必须人工理解后再提交

## 推荐团队工作方式

对于每个功能，建议按这个顺序协作：

1. 在群里或 issue 中明确需求范围
2. 如果需求较大，先补 OpenSpec 或设计文档
3. 从 `main` 开新分支
4. 编码
5. 本地自测
6. Push 分支
7. 发 PR
8. Review
9. 修 review 意见
10. 合并到 `main`

## 当前项目最少执行标准

考虑到项目当前规模，团队至少要执行到这一步：

- 不直接在 `main` 开发
- 一人一分支
- 提交前先自测
- 合并前至少 1 人同意
- 涉及高风险模块至少 2 人同意

如果这五条都做不到，后面联调和答辩阶段会非常容易失控。

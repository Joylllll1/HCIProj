## Context

NJU树洞是一个校园匿名社区平台，核心特性是"帖子级匿名"——同一用户在不同帖子中显示不同匿名名。当前系统已有基础功能，但缺少完整的内容治理能力：

- 用户举报功能存在（ReportModal.jsx），但数据存 localStorage，无法持久化
- AdminPage.jsx 有骨架，但"删除内容"和"驳回举报"共用同一逻辑，功能不完整
- 后端缺少 Admin 相关路由、控制器、模型
- User 模型已有 `role: 'admin'` 字段，但未使用

管理员需要一个独立后台，处理举报、追溯身份、封禁用户、删除内容，并记录审计日志。

## Goals / Non-Goals

**Goals:**

- 管理员登录后进入独立后台，与普通用户视图完全分离
- 举报聚合显示，支持追溯发帖人身份、封禁用户、删除帖子
- 封禁/解禁流程完整，含邮件通知
- 所有敏感操作记录审计日志

**Non-Goals:**

- 多管理员账号管理（当前只有一个管理员）
- 管理员在普通树洞中发帖/评论（角色分离）
- 封禁邮件回复功能（仅提供 QQ 联系方式）
- 审计日志 IP 记录（单管理员场景）

## Decisions

### 1. 管理员入口方案

**选择**：登录时根据 `User.role` 判断，管理员直接进入后台，普通用户进入首页。

**理由**：
- 角色分离清晰，避免管理员误操作普通用户功能
- 前端实现简单，登录响应返回 `role`，前端据此跳转
- 不需要"切换视角"功能（管理员不使用普通树洞）

**替代方案**：
- 入口统一，管理员侧边栏显示"管理后台"按钮 → 需要权限判断逻辑，增加复杂度

### 2. 举报数据模型

**选择**：按 `postId` 聚合举报，存举报次数和举报原因数组。

```javascript
Report {
  postId: ObjectId,
  reportCount: Number,
  reasons: [{ reason: String, reportedBy: ObjectId, createdAt: Date }],
  status: 'pending' | 'processed',
  createdAt: Date,
  updatedAt: Date
}
```

**理由**：
- 同一帖子多次举报，前端只需显示一条记录
- 保留举报原因历史，方便管理员了解举报细节
- `status` 字段用于区分待处理/已处理（虽然当前设计是处理后删除，但预留扩展性）

### 3. 封禁数据模型

**选择**：封禁记录独立存储，关联用户和帖子。

```javascript
Ban {
  userId: ObjectId,
  relatedPostId: ObjectId,  // 关联的举报帖子
  reason: String,
  days: Number,
  bannedBy: ObjectId,       // 预留，当前单管理员可省略
  expiresAt: Date,
  isActive: Boolean,
  createdAt: Date
}
```

**理由**：
- `relatedPostId` 让管理员解禁时能回溯"因为什么被封"
- `expiresAt` 用于自然到期判断，`isActive` 用于提前解禁标记
- `bannedBy` 预留给未来多管理员场景

### 4. 匿名追溯实现

**选择**：通过 `Post.ownerUserId` 直接查 `User` 表获取邮箱。

**理由**：
- 后端已存真实 `ownerUserId`，追溯就是简单的数据库查询
- 不依赖前端匿名名（"Alice" 等），避免前后端不一致
- 追溯操作必须记录审计日志

**流程**：
```
管理员点击"追溯" → 弹出输入框填原因
→ 后端验证原因非空
→ 查 Post.ownerUserId → 查 User.email
→ 创建 AuditLog 记录
→ 返回邮箱 + 活跃统计
```

### 5. 封禁邮件模板

**选择**：系统模板自动填充，帖子摘要截取前 50 字。

```
主题：【NJU树洞】账号禁言通知

同学你好，

你的账号因 "[管理员填写的禁言原因]" 被禁言 [X] 天。
禁言期间无法发帖和评论。

相关内容：
[帖子标题]
[帖子内容前50字]...

如有疑问，请联系 QQ: [配置的联系QQ]。

— NJU树洞管理团队
```

**理由**：
- 自动填充减少管理员操作负担
- 显示帖子摘要让用户知道是哪条内容
- QQ 号作为配置项，方便修改

### 6. 自然到期解禁

**选择**：用户登录或发帖/评论时检查 `Ban.expiresAt`，过期则自动解禁。

**理由**：
- 不需要定时任务轮询（减少复杂度）
- 用户触发时检查，性能开销小
- 解禁后发邮件通知（异步发送，不阻塞请求）

**替代方案**：
- 定时任务每分钟扫描过期封禁 → 实现复杂，实时性要求不高

## Risks / Trade-offs

| 风险 | 缓解措施 |
|------|----------|
| 封禁邮件发送失败 | 异步发送 + 日志记录，不阻塞封禁操作 |
| 用户绕过封禁（注册新号） | 校园邮箱唯一，封禁邮箱即可；极端情况需人工处理 |
| 追溯权限滥用 | 强制填写原因 + 审计日志，事后可追责 |
| 举报聚合后丢失细节 | `reasons` 数组保留所有举报原因和时间 |
| 自然到期解禁延迟 | 用户登录时触发，最多延迟到下次登录 |

## Migration Plan

1. **后端新增模型和路由**（无数据迁移）
2. **前端改造 AdminPage**（覆盖现有骨架）
3. **登录逻辑调整**（根据 role 跳转）
4. **测试验证**：举报 → 追溯 → 封禁 → 解禁完整流程

无需数据迁移，新功能增量部署即可。
